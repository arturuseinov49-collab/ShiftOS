# ShiftOS 0.2 · Сценарии смены

Демо отвечает на конкретные вопросы управляющего: готов ли участок, где задержался заказ,
кто устраняет проблему, почему поставка не сходится, какой результат смены.
У каждого отклонения есть факт, источник и следующий шаг. Визуальный статус задачи
сам по себе не означает, что заказ отдан или недостача устранена.

## Попробовать за пять минут

1. **Обзор / Помощник.** Заказ #1502 задержан на кухне: 22 минуты при нормативе 20.
   Нажмите «Назначить разбор»: задача у ответственного кухни, повтор не создаётся.
   В «Заказах» отметьте обе позиции кухни готовыми — соответствующее отклонение исчезнет.
2. **Кухня · бар · зал.** Выберите ответственного, время работы и норматив участка.
   «Подготовить смену» ставит задачу по стандарту этому ответственному один раз за смену.
3. **Задачи.** Назначьте задачу Марии Кузнецовой в зале. Вверху выберите роль
   «Сотрудник» и Марию: начать работу → описать результат → передать на проверку.
   Выберите «Администратор», примите результат или верните на доработку.
4. **Чек-листы.** Сотрудник бара отмечает готовность своего участка.
   Неотмеченный пункт означает отсутствие подтверждения, а не вывод о поведении человека.
5. **Накладные.** В ПН-0929-01 примите 19 кг тыквы вместо 20, укажите недостачу.
   Оплата заблокируется. Укажите основание исправления и примите исправленный документ:
   оплачиваемая сумма пересчитается по фактическому количеству, прежний комментарий сохранится.
   Владелец может отметить оплату. Это запись в демо, деньги не переводятся.
6. **Финансы.** Владелец выбирает день / 7 / 30 дней и заведение / сеть, добавляет расход.
   Операционный результат сразу меняется, в том числе на убыток. Доступен CSV.
7. **Интеграции.** Для «Север бистро» настройте iiko, импортируйте пример дважды:
   второй запуск не добавит повторов. Для «Искра бар» аналогично проверьте r_keeper.

## Возможности ролей

| Роль          | Работа                                                                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сотрудник     | Свои задачи и свободная очередь своего участка, чек-лист участка, приготовление своих позиций; зал закрывает полностью готовый заказ; меню и опубликованное обучение |
| Администратор | Настройка участков, команда, все задачи и проверка, очередь заказов, приёмка и разбор расхождений                                                                    |
| Владелец      | Операции администратора, P&L и сеть, расходы, отметка оплаты, настройки POS                                                                                          |

Все новые сценарии работают **только на вымышленном снимке в браузере**.
Роль демо переключается свободно, это не авторизация. Все исходные данные демо доступны
в браузере; реальные люди и финансовые данные сюда не загружаются.
Рабочий `/workspace` использует Supabase Auth и SQL RLS, не получает fallback-демо.

## Расчёт результата

Суммы хранятся целыми копейками. Выручка = закрытые продажи − скидки − возвраты.
Операционный результат = выручка − себестоимость проданных позиций − расходы периода.
Открытые и отменённые заказы не включаются. Средний чек = выручка / число закрытых заказов.
Накладная показывает закупку и обязательство перед поставщиком: её оплата не уменьшает P&L
повторно поверх себестоимости продаж. Демо не ведёт налоги, амортизацию, движение склада
и полноценный денежный поток; показатель называется операционным результатом, а не чистой прибылью.
Себестоимость демо вымышлена, это не вычисление по рабочим ТТК.

## POS без привязки бизнес-логики к поставщику

`src/modules/integrations/contracts.ts` задаёт нормализованный контракт заказов и накладных,
`demo-adapter.ts` реализует пример без сети. Ключ идемпотентности заказа:
провайдер + подключение + внешний ID. Повтор демо-пакета сохраняет уже внесённые изменения.
Это проверка сценария первичного импорта; обновления реальных заказов, курсоры, конфликты
и повторная доставка потребуют отдельного серверного адаптера и хранения состояния синхронизации.
Для одной точки допускается один активный источник продаж, чтобы не задвоить выручку.
Разные точки сети могут использовать разные POS; отдельное подключение может импортировать только склад.

Доступность реальных потоков зависит от версии, лицензии и конфигурации клиента.
Для iiko выбор между Cloud и Server уточняется по [официальной документации iiko](https://ru.iiko.help/home/ru-ru/).
Для r_keeper предусмотрена граница адаптера к [White Server API](https://docs.rkeeper.ru/ws/white-server-api-27844345.html),
складские документы рассматриваются отдельно через [StoreHouse](https://docs.rkeeper.ru/sh5).
Наличие этих интерфейсов не означает, что демо уже подключено к кассе.
Реальные ключи должны храниться на сервере в защищённом хранилище, по tenant и соединению;
публичная форма демо не принимает паролей и токенов.

## Следующий спринт: одна настоящая смена

Перенести цепочку назначения, выполнения и проверки задач в Supabase:
смены / участки / история действий с `organization_id`, права на заведение,
привязка сотрудника к аккаунту и защищённые приглашения. Проверить одновременно
два аккаунта в двух организациях и работу с телефона сотрудника.
После этого подключить одну пилотную кассу и сверить закрытые продажи с её отчётом.
Камеры и vision остаются за будущим контрактом событий.
